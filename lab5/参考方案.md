## 2. 推荐优化路径（按优先级排序）

### 优先级 1：确认并切换到专用 Decode GEMV（预期收益：约 7%～15% 端到端）

#### 技术要点

日志明确证明 decode 的 INT4 Linear 是主要瓶颈。原先 `_int4_row_gemv_kernel` 在调用处硬编码 `block_n=1`，导致每个输出列都启动很小的 program；将 N 维 tile 调整为 `block_n=4` 后，在多种 decode shape 上获得稳定收益。

日志 microbenchmark `133870` 的结论：

- 所有测试 shape 的 `max_abs_error_vs_block1=0.0`；
- `block_n=1` 比 `block_n=4` 慢约 20%～30%；
- `block_n=4` 是稳健全局最优；
- `block_n≥16` 因寄存器压力明显变慢；
- 端到端 `62.3983s→57.8831s`，下降 7.24%。

#### 实施步骤

1. 检查当前 `int4_triton.py`/`triton_kernels.py` 是否存在 row GEMV 路径；
2. 确认 `int4_linear()` 的 decode 分支实际传入 `block_n=4`；
3. 对 `M=1,2,3`、以下 shape 分别 benchmark：
   - `q/o_proj`：`K=3840/4096`、`N=3840/4096`；
   - `k/v_proj`：较小 `N`；
   - `gate/up_proj`：`K≈3840/4096`、`N≈15360`；
   - `down_proj`：`K≈15360`、`N≈3840/4096`；
4. 比较 `block_n∈{1,2,4,8,16}`；
5. 用相同输入对比 `max_abs_error` 和完整生成 token 数；
6. 只在 microbenchmark 和端到端都不回退时保留。

#### 关键参数

```text
block_n = 4
rows/M = 1, 2, 3
不要默认使用 block_n >= 16
```

如果当前实现使用同学日志中的 split-K 分支，应先确认它不会覆盖更快的 GEMV 路径。日志后续实验中 `split-K=16` 适合部分小 N shape，但不是所有 N 都收益；日志明确指出 gate/up 的 `N=14336` 测试中 split-K 为负收益。

#### 预期效果

已由日志实测支持的保守预期：

```text
端到端约 7%～10%
```

`20%～30%` 是单个 GEMV kernel 的局部收益，不应直接当作端到端收益。

### 优先级 2：Prefill 使用单独 Dequant Kernel + cuBLAS（预期收益：约 8%～10% 端到端）

#### 技术要点

prefill 中，cuBLAS Tensor Core GEMM 本身很快，主要开销来自 reference `dequantize_weight()` 的多次 elementwise pass。日志确认：

- reference 路径执行 `unpack_int4 + view + cast + sub + mul`，至少 4 次读写；
- 对 `15360×3840` 权重，reference dequant 约 6.09ms，而 cuBLAS GEMM 小于 0.6ms；
- 直接用一个通用 Triton dequant-GEMM 替代 cuBLAS 反而变慢；
- 正确方案是“单独快速 dequant 一次写 BF16 buffer，再调用 cuBLAS `F.linear`”。

#### 实施步骤

1. 对 `rows>16` 的 prefill 输入走独立 dequant 路径；
2. Triton kernel 只负责：
   - 连续读取 packed uint8；
   - 解出两个 nibble；
   - 读取每组 scale/zero；
   - 写出 dense BF16 权重；
3. dequant 完成后使用 `F.linear`；
4. 不要强行把大矩阵 prefill 改成通用 Triton dequant-GEMM；
5. 复用一个扁平 dequant buffer，避免每层重新 `torch.empty`；
6. 如尝试 `torch.addmm` 融合 bias，必须独立 A/B；日志中该尝试只有 0.3% 噪声收益，最终回退到 `F.linear`。

#### 关键参数

日志 v2 的实测最佳配置：

```text
量化 group_size = 64
Dequant BLOCK_K = 64 = group_size
Dequant BLOCK_N = 64
Dequant num_warps = 8
```

日志中失败的 v1：

```text
BLOCK_N=128
BLOCK_K=256
num_warps=4
```

失败原因：

- tile 为 `128×256=32768` 元素；
- FP32 中间值和寄存器压力过高；
- packed INT4 读取不连续；
- scale 重复加载；
- `10.85ms` 比 reference `6.09ms` 慢 1.78 倍。

#### 预期效果

日志实测：

```text
57.88s → 53.21s
端到端下降 8.07%
```

dequant kernel 局部加速：

- gate/down projection 约 5.4～6.8 倍；
- 有效带宽约 124 GB/s；
- 进一步优化空间日志估计小于 10%。

### 优先级 3：复核 `group_size=64` 量化（预期收益：精度改善，性能收益需复测）

#### 技术要点

日志中，GPTQ 的 `block_size` 和量化 `group_size` 作用不同：

- `block_size` 只是 GPTQ 全局误差传播的计算分块参数；
- `group_size` 直接决定 scale 粒度，会改变最终量化结果。

日志实测：

```text
block_size=128 → 64：delta_nll 基本不变
group_size=128 → 64：delta_nll=0.1037372564 → 0.0866560046
```

因此，不要把 `block_size=64` 当成精度优化；应重点验证 `group_size=64`。

#### 实施步骤

1. 使用与最终 kernel 兼容的 W4A16 格式重新量化；
2. 保持统一 group size，不要先做 attention=64、MLP=128 的混合方案；
3. 日志中的混合粒度实验得到 `delta_nll=0.1092193`，差于统一 group 128，已淘汰；
4. 重新执行完整 quality evaluation；
5. 只有 `delta_nll` 达标后再比较性能；
6. 确认 loader、scale layout、Triton dequant/GEMV 都支持 group 64。

#### 关键参数

```yaml
quantization:
  bits: 4
  group_size: 64
  symmetric: true       # 日志该成功 checkpoint 使用对称 INT4
  scale_dtype: float16
gptq:
  block_size: 128       # 日志表明改成 64 没有精度收益
```

当前实现若使用的是非对称 INT4，不能直接套用上面的 `symmetric: true`；必须确认 checkpoint 格式和 kernel 的 zero-point 逻辑。日志成功经验对“group size 选择”适配程度高，对“对称/非对称格式直接切换”适配程度不足，需进一步验证。

#### 预期效果

主要收益是精度：

```text
delta_nll 约降低 0.017
```

性能方面，日志中的 group64 + scale 广播版本曾达到：

```text
elapsed_s=158.9519793
```

但该值属于早期 group128/ring 代码基线，不能直接与当前 89.28s 比较。当前代码必须重新 benchmark。

### 优先级 4：`expandable_segments` + Dequant Buffer 复用（预期收益：0%～5%，主要价值是稳定性）

#### 技术要点

日志中 batch 3 的峰值显存为：

```text
peak_reserved = 9630MB / 10240MB ≈ 94%
```

最大 prefill batch 中，MLP gate/up 输出约 176MB，空闲显存只有约 170MB，触发可恢复的 allocator OOM warning。设置 expandable segments 后：

- OOM warning 消失；
- 性能不降；
- batch 3 更适合 OJ 环境中的不同 allocator 状态。

#### 实施步骤

在任何 `import torch` 之前设置：

```python
import os
os.environ.setdefault("PYTORCH_CUDA_ALLOC_CONF", "expandable_segments:True")
import torch
```

如果 OJ 入口脚本不适合修改，可以在启动命令中设置：

```bash
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
```

同时：

- 将 prefill dequant buffer 改为单个扁平 1D buffer；
- 按需 `view` 成当前权重 shape；
- 避免每层分配约 100～120MB 的临时 tensor；
- 确认 buffer 不会在并发 forward 时被错误复用。

#### 预期效果

日志中主要是稳定性收益：

```text
batch3 无 expandable_segments：有可恢复 OOM warning
batch3 + expandable_segments：无 warning，性能不降
```

不应把它宣传为稳定的 10% 性能优化。

### 优先级 5：Continuous Batching + Chunked Prefill 参数复现（预期收益：约 15%～30%，取决于当前实现）

#### 技术要点

日志中 batch 2→3 的主要收益之一来自减少 prefill 次数：

```text
6 个 batch（4×bs2 + 2×bs1）
→ 4 个 batch（3×bs3 + 1×bs1）
prefill 次数下降 33%
elapsed_s: 53.21s → 45.67s
```

后续 continuous batching + chunked prefill 的结果更明显：

| Chunk size | elapsed_s | generated tokens |
|---:|---:|---:|
| 768 | 95.0668 | 320 |
| 896 | 97.3719 | 316 |
| 1024 | 91.7657 | 320 |
| 1152 | 82.9590 | 273 |
| 1280 | 83.7076 | 273 |
| 1536 | 82.9622 | 273 |

日志最终选择：

```text
HPC101_PREFILL_CHUNK_SIZE=1152
```

#### 实施步骤

1. `Runner` 不再每 3 条请求切成独立静态组，而是将完整等待队列交给 engine；
2. engine 维护：
   - waiting queue；
   - running slots；
   - free slots；
   - completed requests；
3. 请求完成后立即释放 slot；
4. 从 waiting queue 补充新请求；
5. prefill 受 token budget 限制，使用 chunk size 1152；
6. decode 优先于新 prefill；
7. KV cache 必须按 slot 写入、读取、commit。

#### 关键参数

```text
scheduler_backend = continuous_batch
max_batch_size = 3
scheduler_batch_size = 3
HPC101_PREFILL_CHUNK_SIZE=1152
```

若当前 OJ 的 token 数与日志不同，应比较：

- generated token 数是否一致；
- 请求顺序是否一致；
- 是否因 chunk 边界改变 argmax/EOS；
- elapsed 是否在相同输出 token 数下比较。

日志明确发现：

- chunk size 1024 以下有时生成 320 token；
- chunk size 1152/1280/1536 生成 273 token；
- chunk 边界可能改变浮点累加顺序和 EOS/argmax；
- 不能只看 elapsed，必须同时记录 generated_tokens。

#### 预期效果

日志实测从旧版本约 148s 量级降至约 83s 量级，但该收益包含同学的 kernel、scheduler、量化和环境差异。对当前已有 continuous batching 的实现，建议保守预期：

```text
额外收益约 5%～20%，需实测
```

### 优先级 6：FP8 Sliding KV Cache，尝试解锁 Batch 4（预期收益：约 15%～30%，精度风险中高）

#### 技术要点

日志显存预算：

```text
INT4 权重       ≈ 6.4 GB
embed_tokens     ≈ 2.0 GB BF16
KV cache bs3     ≈ 1.15 GB
临时激活         ≈ 0.45 GB
总计             ≈ 9.96 GB
```

batch 4 时：

```text
KV cache ≈ 1.54 GB
MLP 中间 ≈ 235 MB
总计 > 10.24 GB
```

因此 BF16 KV 下 batch 4 不可行。日志后期通过 FP8 sliding KV cache 节省约 1.1GB，解锁了 `bs4 + fp8` 路径。

#### 实施步骤

1. 只先对 sliding-attention KV 使用 FP8；
2. full-attention KV 先保持 BF16，降低精度风险；
3. 明确 FP8 的 scale 保存位置和更新规则；
4. 对写入 KV 做量化，对读取 KV 做反量化；
5. 先运行 unit test 和 dense attention diff；
6. 再运行完整 quality evaluation；
7. 只有 `delta_nll<0.16` 才进入性能比较；
8. batch 4 发生 OOM 或精度不达标时立即回退 batch 3。

#### 关键配置

日志最终提交状态记录为：

```text
batch_size = 4
max_batch_size = 4
kv_cache_dtype = fp8
synchronize_metrics = false
```

但日志没有给出完整 FP8 scale 结构和量化误差定义，因此这部分必须标记为：

```text
需进一步验证
```

#### 预期效果

日志同学观察到：

- batch 4 将 decode step 数从约 124 降至约 93；
- FP8 KV 释放约 1.1GB；
- 最终冷启动约 33.6～33.8s。

对于当前代码，不能直接承诺相同结果；建议保守预期：

```text
端到端约 15%～30%
```

前提是 FP8 质量通过，且 batch 4 没有新的 allocator/CUBLAS 问题。

### 优先级 7：真实生产 Shape Warmup + Dummy Pipeline（预期收益：冷启动约 4～5s）

#### 技术要点

日志诊断明确区分了两类 warmup：

1. 只编译 Triton kernel 的 shape warmup；
2. 真正执行完整 prefill/decode pipeline，触发 cuBLAS plan autotune 和 caching allocator settle。

只完成第 1 类 warmup 后：

```text
run1_cold ≈ 38.16s
run2_warm ≈ 33.63s
cold→warm gap ≈ 4.53s
```

在未计时的 engine init 中执行一次 production-shaped dummy generation 后：

```text
run1_after_dummy ≈ 33.96s
run2_warm ≈ 33.92s
gap ≈ 0.04s
```

#### 实施步骤

1. 从量化模型 manifest 动态收集真实 `(out_features, padded_in_features)`；
2. 不要写死一个生产中不存在的 shape；
3. 覆盖 dequant 和 GEMV 两条路径的全部 shape 特化；
4. 在 engine 初始化且外层 `perf_counter` 开始之前执行 dummy pipeline；
5. dummy 输入使用合法 token id；
6. dummy shape 接近生产最大 batch 和长 prompt；
7. dummy 后恢复：
   - `_batch_size`；
   - KV cache 状态；
   - random seed；
   - 任何 scheduler 状态；
8. 将 warmup 逻辑限定在性能后端，例如 `linear_backend == "int4_triton"`；
9. quality 的 `int4_reference` 路径不要引入同样的额外开销或数值变化。

#### 推荐伪代码

```python
# engine.__init__，外层计时开始前
if linear_backend == "int4_triton":
    shapes = collect_real_manifest_shapes(model)
    warmup_kernels(shapes)
    warmup_full_pipeline(
        batch_size=max_batch_size,
        prompt_length=max_sequence_length - 2,
        decode_steps=2,
    )
    reset_cache_and_rng()
```

#### 预期效果

日志三个独立冷启动结果：

```text
33.65s / 33.80s / 33.71s
均值 33.72s，极差 0.15s
```

对比旧冷启动约 38.5s，净减少约 4.9s。当前实现应先确认 `run_generation_queue.py` 的计时起点，保证 warmup 确实在计时区间外。

## 3. 已被验证失败的尝试（避免重复）

### 3.1 GPTQ `block_size=128→64`

- 失败/无收益原因：`block_size` 只是 GPTQ 误差传播的计算分块，不改变最终量化结果；日志中 `delta_nll=0.1037372564` 基本不变。
- 结论：不要单独为了精度把 block size 改成 64。保留 `block_size=128`，优先验证 `group_size`。

### 3.2 混合 group size：Attention=64、MLP=128

- 实测：`delta_nll=0.1092193`，差于统一 group 128。
- 根本原因：逐层误差传播存在非线性耦合，局部选择更小 group 并不保证全局 NLL 更好。
- 结论：不要默认使用混合粒度；先测试统一 `group_size=64`。

### 3.3 直接提高 Triton 融合 matmul 阈值覆盖大 prefill

- 实测：rows≥128 时比 reference 慢约 2 倍；rows=3534 时慢约 26 倍。
- 根本原因：大 prefill 矩阵由 cuBLAS Tensor Core 更擅长；通用 Triton 逐 tile 反量化-GEMM 的利用率不足。
- 结论：大 prefill 应采用“快速单独 dequant + cuBLAS `F.linear`”，不要强行使用通用 fused matmul。

### 3.4 Dequant v1：`BLOCK_N=128, BLOCK_K=256, num_warps=4`

- 实测：10.85ms vs reference 6.09ms，慢 1.78 倍；对应端到端回归到约 71.55s。
- 根本原因：tile 太大、寄存器溢出、packed 读取不连续、scale 重复加载。
- 结论：使用 `BLOCK_N=64`、`BLOCK_K=group_size=64`、`num_warps=8` 作为起始点。

### 3.5 `torch.addmm` 替代 `F.linear`

- 实测：`53.55s` vs `53.38s`，差异约 0.3%，在 JIT/环境噪声内。
- 另有一次因为 3D 输入 `view_as(inputs)` 形状处理错误而失败。
- 结论：保留更简单的 `F.linear`，不要因为理论上的 bias epilogue 盲目替换。

### 3.6 Attention GQA 广播替代 group loop

- 假设：将 full attention 中按 group 的多次 matmul/softmax 合并为广播 matmul，减少 launch。
- 实测 A/B：broadcast 约 36.94～45.18s，loop 约 32.98～33.07s；广播回归约 4s。
- 根本原因：广播后 effective M=1，cuBLAS Tensor Core 利用率下降；原 loop 的 batched GEMM effective M 更大。
- 结论：减少 kernel launch 不一定更快；保留 loop 版，先看 effective M 和 GEMM 利用率。

### 3.7 Attention query chunk=512 或只缩小到 128

- chunk=512 仍可能申请约 132MB FP32 probability buffer；设备余量仅 28～70MB，触发 OOM/NVML internal assert。
- chunk=128 能降低单块峰值，但静态 KV cache 长期占用仍使大 Linear 临时权重无法分配。
- 结论：attention chunking 只能缓解短期峰值，不能替代 Ring KV Cache、dequant buffer 复用或 FP8 KV。

### 3.8 Ring KV Cache 的错误 multi-token 实现

- 失败表现：quality `delta_nll=0.7974224`，2048 bucket 明显退化。
- 根本原因：`_score_chunked()` 在首块之后以 multi-token decode 追加时，旧 sliding window 上下文被覆盖/丢失。
- 修复原则：
  - multi-token 增量写 ring 前先读取旧窗口；
  - 与当前 chunk K/V 临时拼接；
  - 使用绝对位置 mask；
  - attention 完成后再写回 ring；
  - 单 token decode 不要无条件拼接 1025 个 key。
- 结论：必须同时测试跨窗口 multi-token append 和 dense attention 差分；不要只测生成路径。

### 3.9 单纯编译 Triton kernel 的 warmup

- 只 warmup 一个不存在的 shape，或者只预热 8 个 Triton shape，不能消除完整 cold→warm gap。
- 根本原因：主要 gap 来自 cuBLAS plan autotune 和 caching allocator 首次生产 prefill settle，而非单纯 Triton JIT。
- 结论：必须执行一次真实 production-shaped dummy pipeline，并确保它位于计时区间外。

### 3.10 Batch 4 在 BF16 KV 下直接尝试

- 日志预算显示 batch 4 总显存超过 10.24GB。
- 失败原因：KV cache 约 1.54GB，加上 MLP 中间激活和 embed BF16 后没有足够余量。
- 结论：没有 FP8 KV 或其他显存释放手段时，不要把 batch 4 作为默认提交配置。

### 3.11 为省显存直接把 embed_tokens 转 FP16

- 日志只说明“未尝试”，因为虽然可能节省约 1GB，但存在精度风险。
- 结论：这是“需进一步验证”而不是已证明成功或失败的方案；除非 FP8 KV 仍不够，否则不应优先尝试。

## 4. 推荐的最终配置

### 4.1 保守可提交配置（不改量化格式）

适用于当前已有 `deltaNLL≈0.11718` 且希望先保持任务一稳定通过的版本：

```yaml
engine:
  dtype: bfloat16
  device: cuda
  max_batch_size: 3
  scheduler_batch_size: 3
  max_sequence_length: 2048
  linear_backend: int4_triton
  scheduler_backend: continuous_batch
  seed: 42
  synchronize_metrics: false

quantization:
  algorithm: gptq
  bits: 4
  group_size: 128       # 若当前 checkpoint 是 group128，不要与 group64 kernel 混用
  scale_dtype: float16
```

环境变量：

```bash
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
export HPC101_PREFILL_CHUNK_SIZE=1152
export HPC101_INT4_BLOCK_N=4
# 仅在代码支持并完成 A/B 后设置：
# export HPC101_INT4_SPLIT_K=...
# export HPC101_CUDA_GRAPH=1
```

> `int4_triton`、`HPC101_INT4_BLOCK_N` 等名称来自日志同学的实现；如果当前仓库使用 `int4_reference` 或其他 backend 名称，应先在代码中确认真实可用值，不能只改 YAML。

### 4.2 冲刺配置：FP8 KV + batch 4

只有以下条件全部满足后才采用：

1. 重新量化/加载后 quality `delta_nll<0.16`；
2. 28/29 项测试全部通过；
3. full/sliding attention dense diff 通过；
4. `performance_public.jsonl` 10 请求 generated token 数与基准一致或差异可解释；
5. batch 4 无 OOM、无 CUBLAS 错误；
6. fresh process 冷启动重复至少 3 次。

候选配置：

```yaml
engine:
  max_batch_size: 4
  scheduler_batch_size: 4
  scheduler_backend: continuous_batch
  synchronize_metrics: false
  kv_cache_dtype: fp8
```

但 `kv_cache_dtype` 是否被当前 `EngineConfig` 接受，必须先检查 dataclass 和 loader；日志没有提供完整字段定义，因此此项必须标记为“需进一步验证”。

### 4.3 Cold-start warmup 配置

推荐将以下逻辑放在 engine 初始化阶段，而不是放在 `run_generation_queue.py` 外层计时之后：

```text
1. 收集 manifest 中所有真实 Linear shape
2. 编译/预热每个 dequant 和 GEMV 特化
3. 运行一次 max_batch × (max_seq_len-2) 的合法 dummy prefill
4. 运行 2 次 dummy decode
5. 清空/重置 cache、batch state、RNG
6. 开始正式计时
```

日志实测预期：

```text
cold start: 约减少 4～5s
```

## 5. 实施注意事项

### 5.1 先做最小 A/B，不要同时改多项

每项优化都要保存：

```text
commit
config
environment variables
GPU/MIG UUID
generated_tokens
elapsed_s
peak_allocated
peak_reserved
quality delta_nll
```

推荐 A/B 顺序：

```text
当前 baseline
→ block_n=4
→ prefill dequant v2
→ expandable_segments + buffer reuse
→ continuous chunk=1152
→ group_size=64 重新量化
→ warmup pipeline
→ FP8 KV + batch4
```

### 5.2 性能比较必须固定输出 token 数

日志中已经观察到：chunk 边界和 batch 排序可能改变 greedy argmax/EOS，导致 273 token 与 320 token 不同。比较时必须同时记录：

```text
requests
prompt tokens
max_new_tokens
actual generated_tokens
elapsed_s
```

如果 generated token 数不同，不能直接用 elapsed 判定优化有效。

### 5.3 精度路径和性能路径分离

日志最终做法是：

- quality evaluation 使用 `int4_reference`；
- performance 使用 `int4_triton`；
- warmup pipeline 只对性能 backend 启用；
- 不让性能专用 buffer/warmup 改变 quality 的 reference 数值路径。

当前实验如果仍只有一个 backend，建议显式增加 backend 分支或至少在 `evaluate_quality.py` 中固定 reference 路径。

### 5.4 CUDA Graph 必须 capture-safe

日志中的 CUDA Graph 方向存在动态状态风险：

- 动态 key length；
- attention mask；
- `index_copy_` target；
- `.tolist()` CPU 同步；
- CPU tensor 与 CUDA tensor copy；
- 不固定的 batch shape。

推荐只捕获：

```text
decode
query_length=1
固定 batch size
固定 cache 地址
固定 output 地址
```

为 batch 1、2、3、4 分别保存 graph；capture 失败时自动回退 eager，不能让 OJ 直接退出。

### 5.5 Ring KV Cache 必须区分 full/sliding attention

日志中最终结构：

```text
40 个 sliding-attention layer：1024-token ring
8 个 full-attention layer：完整 2048-token cache
```

不要对 full attention 也使用 sliding ring。所有 ring view 必须携带绝对 token position，mask 不能直接把物理 ring slot 当逻辑位置。

### 5.6 显存预算

日志中 batch 3 已接近上限：

```text
peak_reserved ≈ 9630 / 10240 MB
```

因此：

- 任何新增临时 BF16/FP32 buffer 都必须做显存预算；
- `torch.cat` 可能造成第二份输出峰值；
- dequant buffer 要复用；
- attention probability 不应完整物化；
- batch 4 只有在 FP8 KV 或其他明确释放显存后才尝试。

### 5.7 JIT 缓存不是唯一冷启动因素

日志显示当 `~/.triton` 因磁盘满无法缓存时，每个 fresh 进程都会重编译；但补全 Triton shape warmup 后仍有约 4.53s gap。真正主要原因是：

```text
cuBLAS plan autotune
+ caching allocator 首次生产 prefill settle
```

因此不能只把精力放在 Triton cache 或简单 dummy Linear 上。

## 6. 推荐执行顺序总结

### 第一阶段：低风险、直接复现

1. 确认 decode GEMV `block_n=4`；
2. 确认 prefill dequant v2：`BN=64、BK=64、num_warps=8`；
3. 启用 `synchronize_metrics=false`；
4. 启用 `expandable_segments:True`；
5. 复用 dequant buffer；
6. 固定 chunk size=1152。

### 第二阶段：性能关键路径

7. 用真实 manifest shape 做 Triton warmup；
8. 在计时区外执行 dummy full pipeline；
9. 对 `M=1/2/3` 分别调 GEMV/small-M/split-K；
10. 用 profiler 验证 decode Linear launch 数和有效带宽。

### 第三阶段：高收益但有精度风险

11. 重新量化统一 `group_size=64`；
12. quality gate 通过后再替换 checkpoint；
13. sliding KV 尝试 FP8；
14. FP8 quality gate 通过后尝试 batch 4；
15. batch 4 fresh process 至少重复 3 次。

### 最终决策规则

```text
如果优化后 delta_nll >= 0.16：立即回退
如果 generated_tokens 改变且无法解释：暂不采用
如果单 kernel 变快但端到端变慢：回退
如果 batch4 偶发 OOM/CUBLAS：不作为默认配置
如果 cold-start 与 warm-start 差异大：补 full pipeline warmup
如果 attention 占比仍低于 Linear：不要优先投入 Flash Decoding
```

## 7. 预期结果

基于日志中的实际数据，可以给出以下分层预期：

| 配置 | 日志证据 | 对当前实现的合理预期 |
|---|---|---:|
| GEMV `block_n=4` | `62.3983→57.8831s` | 约 5%～10% |
| Prefill dequant v2 | `57.88→53.21s` | 约 5%～10% |
| Batch 3 + expandable segments | `53.21→45.67s` | 约 10%～20% |
| Continuous chunk=1152 | 82.9590s，273 tokens | 需结合当前版本复测 |
| Full pipeline warmup | `38.5→33.6s` | 冷启动减少约 4～5s |
| FP8 KV + batch4 | 最终 `33.63～33.80s` | 高收益，但适配/精度需验证 |

不应把所有日志收益简单相加，因为这些实验的基线、量化 group size、backend、batch、KV dtype 和输出 token 数并不完全一致。

**推荐最终目标路径：**

```text
先确保当前 89.28s 版本复现稳定
→ 复现 chunk=1152 与 block_n=4
→ 加入真实 shape + full pipeline warmup
→ 重新量化 group_size=64 并做 quality gate
→ 尝试 FP8 sliding KV 解锁 batch4
→ 仅保留 fresh OJ 测试中最稳定的配置
```
